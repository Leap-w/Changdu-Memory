### 1.4 数据流向

```
用户操作 → 页面组件 → Pinia Store → Repository → Supabase REST API → PostgreSQL
                                                    │
                                                    └─ Storage (图片文件)
```

- **认证流**：`main.ts` 启动时调用 `authStore.initialize()` → Supabase `getSession()` → 恢复登录状态
- **数据加载**：页面 `onMounted` 检查 Store 是否已有数据，没有则调用 `loadXxx()`
- **数据保存**：Repository 层获取 `auth.getUser()` 得到 `user_id`，写入时自动关联用户
- **图片上传**：统一使用 Supabase Storage bucket `photos`，路径格式 `{userId}/{entity}/{entityId}/{timestamp}.{ext}`
- **无实时同步**：所有数据操作均为请求-响应模式，无 WebSocket/实时订阅

### 4.3 数据关系

```
profiles (1:1 auth.users)
time_profile (1:1 user)
countdowns (1:N user)
diaries (1:N user) → diary_photos (1:N diary), diary_tags (N:M tags)
work_plans (1:N user)
todos (1:N user)
expenses (1:N user)
schedules (1:N user)
students (1:N user)
assets (1:N user)
welfare_items (1:N user)
memories (1:N user) → memory_photos (1:N memory)
```

### 4.4 软删除 vs 硬删除

- **软删除** (4张)：`diaries`, `todos`, `work_plans`, `expenses` — `deleted_at` 字段，支持回收站
- **硬删除** (其余14张)：直接 `DELETE`，不可恢复

### 4.5 Storage 路径规范

| 实体 | 路径格式 |
|------|----------|
| 头像 | `{userId}/avatars/{userId}_{timestamp}.{ext}` |
| 日记图片 | `{userId}/diary/{diaryId}/{timestamp}-{random}.{ext}` |
| 大事记图片 | `{userId}/memory/{memoryId}/{timestamp}.{ext}` |

## 第六部分：代码质量检查

### 6.1 当前已知问题

| # | 问题 | 影响 | 建议 |
|---|------|------|------|
| 1 | **Home.vue 内联实现过多** (~500行) | 维护困难 | 用已有独立组件替换 |
| 2 | **32 处 `supabase as any`** | TypeScript 类型安全丧失 | 逐步替换为 typed client |
| 3 | **硬删除与软删除不一致** | 部分数据误删无法恢复 | 统一策略 |
| 4 | **Search.vue 全量加载** | 数据量大时首屏慢 | 分页或 Supabase 全文搜索 |
| 5 | **批量操作 N+1** | 批量操作慢 | `Promise.all` 并发 |
| 6 | **无单元测试** | 回归风险 | 添加 Vitest |
| 7 | **无 CI/CD** | 手动部署 | GitHub Actions |

### 6.2 响应式断点

项目使用 `appStore.isMobile` (基于 `window.innerWidth`) 切换布局。各页面内联有独立的响应式断点 (400/500/599/600/767/768/899/900px)，碎片化较严重，但当前功能正常。

  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  -- 业务字段
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now()

CREATE TRIGGER set_xxx_updated_at
  BEFORE UPDATE ON public.xxx
  FOR EACH ROW EXECUTE FUNCTION public.update_updated_at_column();
ALTER TABLE public.xxx ENABLE ROW LEVEL SECURITY;
DROP POLICY IF EXISTS "xxx_select" ON public.xxx;
CREATE POLICY "xxx_select" ON public.xxx FOR SELECT  USING (auth.uid() = user_id);
CREATE POLICY "xxx_insert" ON public.xxx FOR INSERT  WITH CHECK (auth.uid() = user_id);
CREATE POLICY "xxx_update" ON public.xxx FOR UPDATE  USING (auth.uid() = user_id);
